# Working on testlanes

Read [Contributing](CONTRIBUTING.md) and [Design](DESIGN.md) before changing code.

## Scope and Invariants

testlanes plans runtime-balanced Vitest, Jest, and node:test shards, runs them on GitHub Actions, and keeps per-file timing history in Actions artifacts. It is a port of [parallel_tests-ci](https://github.com/dblock/parallel_tests-ci); keep its trust and retry rules. Non-goals are a hosted service, other CI providers, dynamic queue mode, automatic shard sizing, splitting within a file, and Playwright or Cypress.

Source lives in `src/` as ESM JavaScript with JSDoc types; `types/` is generated by `npm run types` during `npm pack` and is not committed. Do not add a runtime build step or TypeScript sources. The CLI is `bin/testlanes.js` and `src/cli.js`; reporters are in `src/reporters/`; the reusable workflow is `.github/workflows/testlanes.yml`; the standalone action is `action.yml`. Tests live in `test/`, and runner fixture projects in `fixtures/`.

- Discover Vitest and Jest files through the runners' own listing commands, and node:test files through the default `node --test` patterns, unless `pattern` is set; do not reimplement runner configuration resolution.
- Remove `NODE_TEST_CONTEXT` from the environment of spawned `node --test` runs.
- Partitioning is deterministic: identical files, sizes, and timings produce identical plans.
- Missing timings stay unknown, never zero-duration.
- Only successful same-repository default-branch push runs publish baselines; PRs and forks only read them.
- Never execute artifacts, persist checkout credentials, or use `pull_request_target`.
- Use public Vitest and Jest reporter and CLI APIs, not internal imports.
- Pass Vitest files as absolute paths before any options, never after `--`, and verify that a shard measured exactly its assigned files.
- Workflows run the caller's installed CLI with `npx --no-install`; keep third-party actions pinned by commit and pass inputs to the CLI through `TESTLANES_INPUTS` and other environment variables, never by interpolating them into commands, except the caller-supplied `install-command` and `setup` scripts.
- Keep `TESTLANES_VERSION` in `action.yml` equal to the package version, and the README install, workflow, and action pins on the latest released version; `npr.config.js` updates both during releases. The reusable workflow carries no version, and release references must never name files under `.github/workflows/`, which the release workflow's `GITHUB_TOKEN` cannot push. Keep one reusable workflow selected by its `framework` input rather than per-framework wrappers.
- With `install-node-version`, install, plan, and collect on it, and switch Test jobs to `node-version` before `setup` and the shard run.
- Apply `test-wrapper` only to shard runs, never to file listing, and keep `artifacts` uploads `if: always()` with one overwritten artifact per shard.
- Keep `testlanes.yml` steps single and OS-independent: logic belongs in `testlanes github <step>`, which reads `TESTLANES_INPUTS`, not in Bash or PowerShell. The pre-install Detect Package Manager step is JavaScript run with `shell: node {0}`. `install-command` and `setup` are the caller's own scripts, run as the step body with the runner's default shell.
- Error and help messages are full sentences ending with periods.

## Setup and Validation

Use Node.js `26.13.1` from `.nvmrc`. The package supports Node.js 22.12 or newer. Run `npm ci`, `npm test`, and `npm run lint` before every commit and push; `npm test` includes the packed-consumer suite, which `npm run package:check` runs alone. Inspect coverage with `npm run test:coverage` and aim close to 100% of runtime code with meaningful tests, preferring real Vitest, Jest, and node:test subprocesses against `fixtures/`. Check workflows with `actionlint`. Verify current stable releases when updating dependencies or GitHub Actions.

Generate `assets/logo.svg` only with `npm run logo` from `scripts/logo.js`, keep it first in README at 160 pixels with descriptive alternative text, and keep it in the npm archive; see [Artwork](DESIGN.md#artwork). Keep Markdown paragraphs on one line, title-case Markdown headings and YAML display names, and add only reviewed words to `.spellcheck.txt`. Keep Test, Lint, and Package workflows separate, with explicit inline `matrix.entry` combinations and no `include` or `exclude`. Keep the packed-consumer test independent of `npm pack --json`, whose output differs between npm 11 and the release workflow's npm 12.

## Git and Pull Requests

Work on `<username>/<topic>` branches in the main checkout, using sibling worktrees only for parallel work. Stack multiple changes as small PRs registered with `gh stack link`, keep one coherent commit per PR, update task-owned branches with `--force-with-lease`, merge with rebase merges only, and never force-push or directly push development changes to `master`. Add CHANGELOG entries with the actual PR number and author for features, improvements, and fixes. Include an AI co-author trailer in AI-assisted commits and disclose AI authorship in PR descriptions and comments. After a PR merges, fetch with pruning, verify the merge on GitHub, and remove only clean, task-owned branches and worktrees.

Do not merge, publish, tag, create releases, dispatch `release.yml`, configure credentials, or overwrite published versions without explicit authorization. The release workflow is the only exception to PR-based development: it pushes the release commit, tag, and next-development commit directly to `master`. See [Releasing](RELEASING.md).
